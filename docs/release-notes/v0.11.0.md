# v0.11.0

## Remote Sessions: Drive One Machine's Agents From Another

Agent Dock can now host its live sessions for a second copy of Agent Dock running on a different
machine. The machine hosting keeps doing all the work — it owns the Claude processes, the files and
the git repositories. The second machine is a remote screen and keyboard for it.

- **File → Remote → Enter Server Mode…** starts hosting. You choose a port (default 7420), the port
  is **bind-tested before the server starts** rather than guessed at — and if it's taken, the dialog
  offers the next free one instead of just refusing
- **File → Remote → Connect to Server…** on the other machine. Enter an **IP address, hostname or
  domain** and the port, and connect. Connecting happens *before* you're asked for anything secret,
  so you can see **which machine answered** and its identity fingerprint first
- Then enter the **eight-character pairing code** shown on the host's status strip. The code uses an
  alphabet with no `0`/`O`, `1`/`I`/`L` or `U` — the glyphs people misread when copying a code from
  one screen to another — and it's accepted however you type it: with or without the dash, in any case
- The client builds a **single group named after the host machine**, holding one tab per live session
  there. Previous conversation history loads into each chat panel, and the layout is yours to
  rearrange — it's your window, not a mirror of the host's
- **The file explorer, git status, file preview, todo list and project description all come from the
  host.** Click a file on the client and its content is fetched from the other machine and
  syntax-highlighted locally
- Type into the chat as you normally would. The message is sent to the host, which runs it and
  streams the response — thinking, tool calls, the answer, cost and token counts — back to you

## Remote Sessions: One Driver At A Time

- **Entering server mode makes the host's agent interaction inert** — the composer, send, the queue
  and schedule controls, and the inline permission and question panels. The human is at the other
  machine, so that's where prompts get answered. Everything else on the host stays usable
- **Stop Server is never disabled**, which is how someone who walks back to the host reclaims control
- **One client at a time.** A second connection is refused and told who currently holds it
- A persistent **status strip** shows what's happening on both sides: hosting shows the address, the
  pairing code, who's connected, and buttons to copy the code, **Take back control**, or stop. The
  client shows which machine it's driving, and its window title says so too — a remote window that
  looked identical to a local one would be a way to run the wrong command on the wrong machine
- **Disconnections explain themselves.** "The server stopped hosting", "The server took back
  control", "The pairing code was regenerated", a version mismatch and a dropped link are five
  different messages, not one generic failure
- **A dropped connection reconnects itself** using a token issued at pairing, so a Wi-Fi blip doesn't
  ask you to type the code again. The transcript stays on screen and is marked stale rather than being
  cleared — then patched when the link returns

## Remote Sessions: What It Costs You To Trust It

Hosting is exactly as powerful as it sounds, so the first time you enable it you have to acknowledge
what it allows: **a paired client can instruct an agent that reads, writes and runs commands on the
hosting machine.**

- The connection is **TLS with a self-signed certificate** generated once and kept, and the client
  **pins its fingerprint on first pairing**. A changed fingerprint on a later connect is a prominent
  warning, not a silent accept
- The pairing code proves *authorization*; the pinned certificate proves *identity*. The code itself
  never crosses the wire — the client answers a challenge with a keyed proof
- **Pairing attempts are rate-limited** and lock out after repeated failures, which is what makes an
  eight-character code sufficient
- **Every file request from a client is containment-checked** against the project root and size-capped
- The client needs **no Claude Code install and no Anthropic login** — all credentials, accounts and
  usage stay on the hosting machine
- Prefer a VPN over forwarding the port on your router. The port is not something to expose to the
  internet

## Remote Sessions: Reading Files Without Hammering The Network

- File contents are cached on the client under a **version token**, so viewing the same file twice
  doesn't re-transfer it — the host answers "unchanged" in a single small frame
- Because the agent is continuously rewriting the repository, **invalidations ride the same watcher
  that drives git status**. Files the agent touches are marked stale and re-fetched next time you look
  at one, rather than being polled for or served stale
- The explorer fetches a directory's children **when you expand it**, so a large repository is never
  shipped wholesale

## File Explorer: No More Flicker When The Agent Edits Files

- Refreshing the file tree used to **clear it and rebuild it**, then try to put your expanded folders
  back afterwards. Because the refresh is driven by the git file watcher, the agent editing files made
  the tree flicker and lose its place. The tree is now **patched in place** — expanded folders,
  selection and scroll position all survive a refresh

## Internals: Services Are Injected, Not Global

Groundwork for the remote feature, and for supporting agents beyond Claude Code.

- Every service that holds state or touches the outside world is now an **instance behind an
  interface**, resolved from a container at startup: logging, app and project settings, workspace
  files, theming, accounts, usage, sounds, the taskbar icon, markdown rendering, image attachments,
  update checks and release notes
- `ClaudeSession` no longer carries a global binary path, and is no longer constructed by the chat
  panel — it comes from a factory, which is the seam a remote host substitutes
- The only statics left are dependency-free pure functions and WPF attached properties, neither of
  which has anything to substitute

## Fixes

- The **git status panel** no longer runs git while a project is showing another machine's repository
