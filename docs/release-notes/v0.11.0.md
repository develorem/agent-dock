# v0.11.0

## Remote Sessions: Drive One Machine's Agents From Another

Agent Dock can now host its live sessions for a second copy of Agent Dock running on a different
machine. The machine hosting keeps doing all the work — it owns the Claude processes, the files and
the git repositories. The second machine is a remote screen and keyboard for it.

- **File → Remote → Enter Server Mode…** starts hosting. You choose a port (default 7420), the port
  is **bind-tested before the server starts** rather than guessed at — and if it's taken, the dialog
  offers the next free one instead of just refusing
- **File → Remote → Connect to Server…** on the other machine. Enter an **IP address, hostname or
  domain** and the port, and connect. Connecting happens *before* you're asked for anything secret,
  so you can see **which machine answered** and its identity fingerprint first
- Then enter the **eight-character pairing code** shown on the host's status strip. The code uses an
  alphabet with no `0`/`O`, `1`/`I`/`L` or `U` — the glyphs people misread when copying a code from
  one screen to another — and it's accepted however you type it: with or without the dash, in any case
- The client builds a **single group named after the host machine**, holding one tab per live session
  there. Previous conversation history loads into each chat panel, and the layout is yours to
  rearrange — it's your window, not a mirror of the host's
- **The file explorer, git status, file preview, todo list and project description all come from the
  host.** Click a file on the client and its content is fetched from the other machine and
  syntax-highlighted locally
- Type into the chat as you normally would. The message is sent to the host, which runs it and
  streams the response — thinking, tool calls, the answer, cost and token counts — back to you

## Remote Sessions: The Host Is Obviously A Host

- **The address, not the machine name.** Server mode now shows the machine's **IPv4 address** as the
  thing to type on the client — in the Enter Server Mode dialog before you start, in the status
  strip after, and behind a new **Copy address** button. A Windows machine name only resolves if the
  client's network is publishing matching NetBIOS or mDNS names, which plenty of home routers, guest
  VLANs and VPN links are not. Hover the strip for **every** address this machine can be reached on:
  a developer box with Hyper-V, WSL, Docker and a VPN has several, and the list is ordered so the
  adapter actually carrying traffic off the machine comes first
- **A `SERVER MODE` badge in the title bar**, and a **`Server mode` pill beside the Active tab**.
  Both name what's happening, both say who's connected once someone is, and **both stop hosting when
  clicked**. The status strip sits at the bottom edge of a maximised window, which is exactly where
  someone walking back to the machine doesn't look
- **Server mode switches the window to the Active Projects view** and shows that tab regardless of
  the workspace setting. Active Projects *is* the published set, so this is the only view where the
  host's screen agrees with the client's
- **Input locks from Start Server, not from the first client.** Previously the composer stayed live
  until someone actually connected — so the window you were looking at as you walked away still
  accepted text that would never be sent. It now greys out immediately, **with a notice saying why**
  rather than just going dead, and a project tab opened *while* hosting inherits the lock instead of
  arriving unlocked
- Permission and question prompts are the deliberate exception: they stay answerable on the host
  while **no** client is connected, and lock once one attaches. Locking them from the start would
  park a blocked turn with nobody able to answer it on either machine

## Remote Sessions: The Sounds Go Off Where You Are

- **A hosting machine is now silent.** The whole point of server mode is that nobody is in the room
  with the host, so a chime there reaches nobody who can act on it — and if you're within earshot of
  both machines you hear every notification twice
- **The client plays them instead**, and it uses **the host's per-project sound settings**, which now
  travel with the project in its snapshot. A client reading its own `.agentdock/settings.json` would
  find no such folder — the project lives on the other machine — and would quietly fall back to
  defaults, losing whatever you'd configured on the host

## Remote Sessions: One Driver At A Time

- **Entering server mode makes the host's agent interaction inert** — the composer, send, the queue
  and schedule controls, and (once a client attaches) the inline permission and question panels. The
  human is at the other machine, so that's where prompts get answered. Everything else on the host
  stays usable
- **Stop Server is never disabled**, which is how someone who walks back to the host reclaims control
- **One client at a time.** A second connection is refused and told who currently holds it
- A persistent **status strip** shows what's happening on both sides: hosting shows the address, the
  pairing code, who's connected, and buttons to copy the address, copy the code, **Take back
  control**, or stop. The
  client shows which machine it's driving, and its window title says so too — a remote window that
  looked identical to a local one would be a way to run the wrong command on the wrong machine
- **Disconnections explain themselves.** "The server stopped hosting", "The server took back
  control", "The pairing code was regenerated", a version mismatch and a dropped link are five
  different messages, not one generic failure
- **A dropped connection reconnects itself** using a token issued at pairing, so a Wi-Fi blip doesn't
  ask you to type the code again. The transcript stays on screen and is marked stale rather than being
  cleared — then patched when the link returns

## Remote Sessions: What It Costs You To Trust It

Hosting is exactly as powerful as it sounds, so the first time you enable it you have to acknowledge
what it allows: **a paired client can instruct an agent that reads, writes and runs commands on the
hosting machine.**

- The connection is **TLS with a self-signed certificate** generated once and kept, and the client
  **pins its fingerprint on first pairing**. A changed fingerprint on a later connect is a prominent
  warning, not a silent accept
- The pairing code proves *authorization*; the pinned certificate proves *identity*. The code itself
  never crosses the wire — the client answers a challenge with a keyed proof
- **Pairing attempts are rate-limited** and lock out after repeated failures, which is what makes an
  eight-character code sufficient
- **Every file request from a client is containment-checked** against the project root and size-capped
- The client needs **no Claude Code install and no Anthropic login** — all credentials, accounts and
  usage stay on the hosting machine
- Prefer a VPN over forwarding the port on your router. The port is not something to expose to the
  internet

## Remote Sessions: Reading Files Without Hammering The Network

- File contents are cached on the client under a **version token**, so viewing the same file twice
  doesn't re-transfer it — the host answers "unchanged" in a single small frame
- Because the agent is continuously rewriting the repository, **invalidations ride the same watcher
  that drives git status**. Files the agent touches are marked stale and re-fetched next time you look
  at one, rather than being polled for or served stale
- The explorer fetches a directory's children **when you expand it**, so a large repository is never
  shipped wholesale

## File Explorer: No More Flicker When The Agent Edits Files

- Refreshing the file tree used to **clear it and rebuild it**, then try to put your expanded folders
  back afterwards. Because the refresh is driven by the git file watcher, the agent editing files made
  the tree flicker and lose its place. The tree is now **patched in place** — expanded folders,
  selection and scroll position all survive a refresh

## Internals: Services Are Injected, Not Global

Groundwork for the remote feature, and for supporting agents beyond Claude Code.

- Every service that holds state or touches the outside world is now an **instance behind an
  interface**, resolved from a container at startup: logging, app and project settings, workspace
  files, theming, accounts, usage, sounds, the taskbar icon, markdown rendering, image attachments,
  update checks and release notes
- `ClaudeSession` no longer carries a global binary path, and is no longer constructed by the chat
  panel — it comes from a factory, which is the seam a remote host substitutes
- The only statics left are dependency-free pure functions and WPF attached properties, neither of
  which has anything to substitute

## Chat: Text That Was Being Thrown Away

Three faults in how a turn's output was classified, all of which lost text rather than merely
misplacing it. The worst was most visible around questions: the agent would write up its findings,
ask you to choose, and the findings would be nowhere on screen.

- **Text sharing a message with a tool call was dropped entirely.** `content: [text, tool_use]` is
  an ordinary shape — "here's what I'm about to do" followed by the call — and the tool branch
  returned before it ever read the text blocks. Not folded into the activity bubble, not posted,
  not logged. Gone
- **The preamble to a question is now shown, not hidden.** Text arriving immediately before an
  `AskUserQuestion` (or an `ExitPlanMode` plan approval) was classified as intermediate commentary
  and folded into the collapsed activity bubble — so the question appeared with the analysis you
  needed in order to answer it out of sight. A prompt that stops to ask the human something is not
  a step in the agent's work, and the text leading up to it is now posted as its own visible bubble.
  Work that resumes after you answer opens a fresh activity bubble below it, so the transcript
  still reads in the order things happened
- **A two-part answer no longer shows only its second part.** Text followed by more text, with no
  tool call in between, is one answer arriving across several messages — which is what the CLI does
  when a reply spans stop-reason boundaries. The earlier block was being demoted to commentary and
  hidden. The parts are now joined
- Text before an *ordinary* tool call is still commentary, still folded — that is the whole point of
  the collapsible bubble and it is unchanged

**The classification rules are now pinned by tests.** This is the most regression-prone code in the
app and it had none: every previous attempt to adjust placement broke something else — content in
the wrong order, the collapsible bubble failing to appear, everything dumping into the transcript
root — and none of it was caught before shipping. There are now 22 tests over the state machine,
including guard tests for the behaviour that was already correct. Verified the honest way: all three
faults were temporarily reinstated to confirm the tests go red, and the guard tests stayed green.

## Modes: What This Window Is Doing Is Now A First-Class Choice

Agent Dock was already always in one of four mutually exclusive states, but nothing said so out loud
— the state lived across three different flags, and every place that needed to know "can I do X here"
re-derived it with its own pairwise check.

- A new **Settings → Set Mode** menu lists **Standard, Server Mode, Autopilot, Remote** with a tick on
  the active one. Choosing a different one leaves the current mode for you, rather than making you
  exit it by hand first
- The **title-bar mode badge is now always visible**, not just for the two remote roles — a mode that
  can be armed and then sit quietly needs a label as much as one that's obviously active

## Autopilot: Keep Sessions Moving While Nobody Is Watching

A long task finishes a phase and the agent says it's ready for the next one — then waits, sometimes
for hours, because nobody was there to say "go on then." Autopilot is a new mode for exactly that gap.

- Inside a **nominated time window**, selected sessions that come to rest with nothing waiting on a
  person are nudged to carry on with whatever they can finish alone. Outside the window, nothing
  changes — that's the whole distinction between this mode and Standard
- **Permission prompts and `AskUserQuestion` are never answered by autopilot.** Those are decisions
  for a person, not prompts for it to satisfy
- Nudging respects usage budget, gated on the **worse of the 5-hour and 7-day windows** — below 5%
  remaining, nothing is sent at all
- It waits **a minute after a turn settles** before nudging, and any keystroke pushes that back
- **Three consecutive turns that used no tools** parks the session, so a stuck "nothing left to do"
  loop doesn't burn quota the other sessions could have spent. Any productive turn resets the count
- **Every nudge is posted as its own labeled message**, not disguised as something you typed before
  bed — the morning's transcript stays auditable

## Remote Sessions: Reachable From a Browser, Not Just Another Agent Dock

Server Mode's native client needs a second copy of Agent Dock. Now a plain browser works too.

- A small embedded **HTML/CSS/JS web client** — no framework, no build step — gives a browser the
  tab list (with status dots for working/unread/read), message history, a composer, and full
  question/permission support
- It's deliberately **chat-only**: no file explorer, diff viewer, todo list or scheduling. A
  changed-files list rides along for free since that data was already part of the session snapshot
- The browser listener has **no TLS of its own**, by design — put it behind a reverse proxy (Caddy,
  for one) if you want real encryption or access beyond the LAN. [Remote Sessions](../remote-sessions.md)
  documents the Windows URL-ACL command needed to bind all interfaces, so a first-use `AccessDenied`
  doesn't send you looking in the wrong place
- Under the hood, a WebSocket connection sits alongside the native TLS one on the same single-client
  slot, authenticating through the same HMAC proof and sharing the same lockout budget as native
  pairing — a browser and a native client draw on one failure count, not two

## Tabs: Scrollable Strips At Any Count

Both the group strip and the project strip used to run off the window past a certain number of tabs,
taking the **+** button with them. A pinned leading cluster (**+**, scroll arrows) now stays reachable
at any tab count, and the active tab stays in view while scrolling.

## File Explorer: Shows What's Actually On Disk

Two defects, one root cause — the explorer was answering to git instead of to the filesystem.

- Listings are **no longer filtered through `.gitignore`.** Build output, logs and artifacts — a good
  share of what an agent generates — were invisible; hiding a file the agent just wrote is worse than
  a noisy root
- **Refresh no longer rides the git-status delta event**, which fires only when status rows change and
  missed exactly the cases the tree exists to show: an unversioned folder, a file rewritten while
  already listed as modified, a change committed away. The explorer now refreshes when a session comes
  to rest, on its own subscription

## Chat: Code Blocks Are Native Text Now

Fenced code blocks used to render as an embedded editor control rather than ordinary document text,
which caused three visible problems, all fixed by swapping each fence for a plain paragraph instead:

- **Consecutive code blocks can now be selected and copied as one** — they used to be separate UI
  islands the document's selection couldn't enter
- **Long lines wrap** instead of each block growing its own horizontal scrollbar
- **Links inside code use the theme's link color** instead of a hardcoded blue that was near-invisible
  on dark themes

## Accounts: Customizable Per-Theme Accent Colors

Each account's accent color — usage bar, group box, chat panel header — used to be fixed by its
position in the account list. A new **Colors...** picker in the Claude Accounts dialog lets you set it
per account, with **separate light and dark swatches** since a color that pops on a dark theme can
wash out on a light one. Changes save immediately and refresh every open chat panel header without
waiting for the next usage poll.

## Chat Panels: Tinted Header By Account

The account accent color previously showed only on the usage bar. It's now reused for the chat panel's
header and active-tab bar too, so which login a session is running under is visible at a glance instead
of only readable in the title text. A new **"Color chat panel headers by account"** setting in App
Settings controls this, on by default.

## Fixes

- The **git status panel** no longer runs git while a project is showing another machine's repository
- **Recent workspaces are back under their own heading in the File menu.** The items were inserted
  relative to the separator above Exit, and the new Remote submenu landed in between — so the recent
  files rendered *below* Remote with no divider, leaving "Recent Workspaces" as a heading with
  nothing under it and Remote reading as one of the recent files. They now insert directly after the
  heading they belong to, which is an anchor nothing can be added in front of
